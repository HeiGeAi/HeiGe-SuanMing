## 二、结论先行

外部报告有参考价值，但不能照单全收。10 项建议中：

- 2 项成立并修复：M3、M4。
- 2 项部分成立：M1 是未来维护风险而非当前缺陷；M2 的用户入口已有异常收口，但前置校验与错误信息仍可改进，已修复。
- 3 项属于非阻断工程建议，当前不值得扩改：L3、L4、L6。
- 3 项不成立或建议本身有风险：L1、L2、L5。

更重要的是，独立审计发现了报告未覆盖的真实问题，包括国际日期变更线真太阳时偏移、合婚乙方输入不独立、紫微实际农历年被排盘年覆盖、跨版本 oracle 默认值漂移、许可证“开源”表述不准确，以及 GitHub Action 使用可移动标签。上述问题已在本地候选版本中修复或收准。

当前达到的完成层级：代码和文档已产出，本地 Python 3.13 全量回归、真实 CLI、随机有效输入、静态检查、安全扫描、桌面端、移动端与打印稿均已验证；三组独立复审均为 READY。尚未达到 GitHub 目标环境 CI、Tag、Release 或公开发布层级。

## 四、独立审计发现与修复

### 4.1 八字与合婚，`paipan.py` v1.5.0

1. 真太阳时经度差改为 `[-180, 180)` 的最短角距离，修复国际日期变更线附近等价经度被误算为接近整日偏移的问题。
2. 新增精确对跖点回归，明确 `+180°` 与 `-180°` 都归入负侧，避免未来改成相反的半开区间。
3. 合婚乙方支持独立 `--partner-lng`、`--partner-tz`、`--partner-china-dst` 与 `--partner-lunar`。
4. 乙方可只给年月日并降级为三柱盘，不再伪造时柱、精确起运或真太阳时。
5. `partner_input` 保存历法、时区、经度、时辰是否已知等完整输入口径；`partner_calendar` 仅作为兼容字段保留。

### 4.2 梅花，`meihua.py` v1.2.0

1. 农历小月第 30 日与不存在的闰月会给出明确中文错误。
2. 农历转公历后、晚子推进后的有效年份再次检查 1600 至 2200 范围。
3. `--lunar` 与显式 `--zi-sect` 只允许和 `--time` 同用，不再静默忽略。

### 4.3 六爻，`liuyao.py` v1.2.0

1. `zi_sect` 从 CLI 贯穿到 `build_pan` 与日期上下文，默认值固定为 2，保持旧结果。
2. JSON 在 `日月.子时流派` 记录有效口径，可审计、可重放。
3. `ZHI_WUXING` 改用八字模块单一真源。

### 4.4 紫微，`ziwei.py` v1.3.0

1. 新增 `fix_leap` 与 `year_divide=normal|exact`，并对非法值统一抛出 `ValueError`。
2. `fix_leap=true` 按实际农历日判断：闰月十五日及以前按本月，十六日起按下一月，闰十二月回到正月。
3. `exact` 按 `lunar_python` 的立春精确交接时刻切换排盘采用年，不按整日粗切。
4. 修复发布阻断错误：实际农历年始终写入 `lunar.年干支`，不再被排盘采用年覆盖；排盘采用年与安宫月进入 `calculation`。
5. `input` 保存原始年月日时分、性别、历法与两个策略；文本输出同步展示实际农历日期和排盘口径。
6. 明确记录与 iztro 2.5.8 的边界差异。当前规则在晚子时闰月与立春当日并非完全复刻 iztro，固定锚点不得外推为所有边界一致。

### 4.5 奇门，`qimen.py` v1.2.0

1. 跨年符头四例锁定完整结果，不只断言单个日期字段。
2. 非法干支查找保留 60 步失败上界，并由独立子进程一秒超时测试防止未来回归为死循环。
3. 文档将无法独立重放的外部比对统一降为“历史审查记录”，明确原始版本、输入与输出尚未归档。

### 4.6 发布与文档

1. 总版本升为 `1.16.0`，五引擎版本分别为 `1.5.0`、`1.2.0`、`1.2.0`、`1.3.0`、`1.2.0`。
2. README 中英文测试数同步为 369，并由发布契约测试动态核对六个分项。
3. CI 增加 `v*` Tag 触发，仍复用同一 Python 3.7 与 3.13 测试矩阵。
4. `actions/checkout` 与 `actions/setup-python` 固定到官方 `v4.4.0`、`v5.6.0` 的完整提交 SHA，避免可移动主版本标签漂移。
5. 示例 HTML 去掉脚本动画，保留静态打印样式；版本脚注同步为排盘引擎 `v1.5.0`。
6. 许可证表述从“开源加非商业限制”收准为“源码可用的非商业许可”。OSI 明确要求开源许可证允许商业用途，因此 PolyForm Noncommercial 1.0.0 不是 OSI 定义的开源许可证。该结论是术语核对，不是法律意见。

## 六、残余风险与发布边界

1. Python 3.7 仅做语法级复核。新候选分支尚未推送，因此 GitHub 上没有针对本次改动的 3.7 与 3.13 CI 结果。
2. 奇门历史外部 oracle 的版本、输入、原始输出和转换脚本仍未归档。仓库只能证明固定期望回归，不能独立重放历史比对。
3. 紫微仅有选定锚点与 iztro 2.5.8 比对，且两个边界已知不同。不能宣传“完全对齐 iztro”或“全部公式正确”。
4. Bandit Low B110 位于 `paipan.py` 的可选节气说明构建。失败时只丢失辅助文字，不影响四柱与主结果；当前保留，若未来该字段成为 API 强契约，应收窄异常并增加可观测诊断。
5. `requirements.txt` 固定版本但没有供应链 hash。若要做正式可复现发布，应生成带 hash 的锁定文件，再运行完整依赖解析审计。
6. GitHub 当前没有分支保护或 ruleset。本轮只增加工作流与 Tag 触发，不能把它表述成 required gate。
7. L3、L4、L6 未实施。类型标注、package 化、结构化日志应在出现明确调用方或运维需求时单独立项，不应混进这次边界修复。
8. 工作树尚未提交、暂存、推送、打 Tag 或发布。公开仓库仍是 `v1.15.1` 状态。

## 七、发布建议

本地候选代码已满足进入 PR 与远端 CI 的条件，但不应直接称为“v1.16.0 已发布”。建议顺序：

1. 审阅本地 diff 与本报告。
2. 由项目所有者确认是否接受“源码可用但非 OSI 开源”的公开表述。
3. 提交当前分支并推送，等待 Python 3.7 与 3.13 远端 CI 通过。
4. 视需要启用分支保护或 ruleset，将 CI 设为 required check。
5. CI 通过后再创建 `v1.16.0` Tag 与 GitHub Release。
